# f062637 独立检阅后的收尾状态

## 两项 P2 修正

### 监控回执完整后发布

开始回执、完成回执及 watchdog 输出统一通过 `publish_json_once()` 发布：先在同目录写唯一隐藏暂存文件，flush/fsync 并关闭，再用硬链接将完整文件原子发布到正式路径，最后移除暂存名。Windows 和 POSIX 均拒绝覆盖已存在的正式路径；文件系统不支持硬链接时失败关闭，不降级为可能覆盖旧证据的 rename/replace。发布完成不等于承诺任何存储设备在断电时都不丢目录元数据。

暂存文件不符合正式回执的枚举规则。读取器仍严格核对全部已发布回执和哈希链，不吞 JSON 错误、不跳过损坏历史文件。已有开始回执仍禁止另一写入器复用序号。

已用 f062637 原生产写入器复现“空正式文件→身份未确认通知→写完后恢复通知”。修正后的并发测试暂停在正式发布前，旧回执新鲜时不通知；旧回执超过六分钟时仍告警；损坏已发布回执继续告警。另覆盖 fsync 在发布前、已有同名证据不覆盖、发布失败保留开始证据及禁止续写复用序号。

### 首次完整成功期限

`analyze_source_runs()` 新增 `observed_since_ms` 与 `maximum_initial_success_delay_ms`。开始时间必须由调用方从可信观察起点或来源启用证据提供，绝不以第一条轮询或首次成功时间猜测。分别报告：

- `first_full_success_delay_ms`：开始到首次完整成功的时长；无成功或缺少起点时为 null。
- `maximum_interval_between_full_successes`：两次完整成功间最大间隔。
- `full_success_age_ms`：当前距最后完整成功的时长。
- `waiting_for_first_full_success_ms`：起点已知但尚未成功时，已等待多久。

`initial_success_standard_evaluation` 区分超限、等待首次成功、起点未验证及未配置标准。新增 `source_timing_standard_evaluation` 汇总首次期限和成功间隔；签核不得只读取旧 `gap_standard_evaluation`，后者明确限定为相邻成功及最后成功年龄。总体验收仍为 false。

CLI 安全输入可增加以下结构；该引用由导出者从原回执核对，诊断 CLI 不打开原库，也不声称仅凭引用就独立验证过原回执：

```json
{
  "observation_starts": {
    "company_ir": {
      "observed_since_ms": 1790463867701,
      "basis": "verified_activation_receipt_observation_start",
      "evidence_sha256": "fdc4b456b4a098f31782860131eae9dc5e3e90c02c9b149376887a019ec4ccdb"
    }
  }
}
```

标准文件支持每来源分别配置 `maximum_success_gap_ms` 与 `maximum_initial_success_delay_ms`。旧整数格式仅保留间隔标准，不冒充首次成功期限已配置。开始证据缺失时报告未验证；不完整/非法的引用拒绝处理。标准文件本身不构成授权或签核。

使用已核验的 20260927A 激活回执与冷副本重新计算：SEC 首次完整成功延迟 24.375 秒，Micron 53.572 秒；它们在手册草案的首次期限内，但 Micron 后续间隔仍超限。此分析不追溯批准草案，也不改变已失败的 24 小时验收。

## Windows 监控演练范围

`scripts/rehearse_news_review_monitor_windows.py` 提供一次有界隔离演练，使用新目录、合成身份和健康探针：真实运行定时写入器、独立 watchdog 子进程、独立文件通知接收器；真实暂停完成回执超过六分钟，验证存活但不检查、告警去重、恢复通知及接收确认，最后核对两个子进程正常退出。原生产 watchdog 的六分钟阈值不缩短。

文件接收器的确认不是用户已看到通知。该脚本不安装 Windows 计划任务，不访问真实试验端口、官方来源、模型或数据库，不替代目标环境中已批准的进程/端口/GET 探针。其输出明确保留 `human_notification_channel_verified=false` 和 `production_probe_deployed=false`。正式告警接收位置与部署身份须另行明确。

## 补充发现：前置检查之后到期的最终发送竞态

在 `cebbbd1` 上使用真实 service/controller 和临时合成数据库复现：前置检查通过后，将注入时间推进到原绝对到期，再进入最终发送入口。旧实现仍调用一次模拟传输并记为 REVIEWED；没有真实网络请求。这说明前置时间检查不能代替最终准入瞬间的检查。

`AuthorizedTextRequest` 现增加仅供内存检查的 `admission_check`，在最终发送锁内、标记已准入之前执行。新闻审核再次检查现行累计时钟保护和原绝对授权窗口，不在该锁内读取数据库、写回执或调用停止函数。没有更改现行两秒策略或启用双重截止参考方案。

若在准入前到期或时钟不可信，传输调用为零，保持已有失败处理和永久预约，不归还预算、不重发。Provider 将异常归类后，回执仍保留本地受限错误码 `policy_expired` / `clock_changed`，不会只剩模糊的 `http_not_attempted`。正常停止取消仍按原规则标记 CANCELLED；已准入但结果未知的请求仍保留 UNKNOWN。

55 项相关隔离回归通过、7 项静态检查通过，覆盖前置检查后到期、等待准入锁时到期、时钟异常、直接 service 入口、到期前一毫秒允许一次请求，以及原停止、UNKNOWN、重启与 API pilot 行为。首次针对性测试发现四处错误码丢失，修正后通过；原失败记录保留在独立证据目录。本次结果不等于最新提交完整 CI 通过。
