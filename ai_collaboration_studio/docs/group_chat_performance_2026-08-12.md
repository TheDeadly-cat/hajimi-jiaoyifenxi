# 群聊积压性能收口（2026-08-12）

## 结果

大型失败插话积压场景在不改变公平性、正式轮完成状态和发言合同审计结果的前提下，从冻结基线的 `62.763s` 降至最终完整回归中的 `11.707s`，观察到约 `81.3%` 的耗时下降。

最终后端完整 discovery：`1229/1229`，`844.932s`，网络审计父进程与 Python 子进程越界命中均为 `0`。

## 原因与改动

该场景包含 `103` 条定向插话。每条插话的 Provider 都被显式跳过，但系统仍必须：

1. 持久化失败终态；
2. 保持 FIFO；
3. 最多连续处理两条插话后推进正式发言；
4. 最终完成所有正式成员发言；
5. 生成完整、可验证的发言合同包。

原实现对同一持久状态重复构建完整收敛视图。优化分为两层：

- `_select_next_member` 接受本轮已经计算的收敛视图，避免成员选择再次扫描；
- 连续失败插话之间使用一个长驻的只读 SQLite 观察连接读取 `PRAGMA data_version`。只有事件交还给调用方前后版本完全一致，才允许单次复用；否则立即完整重算。

这不是基于时间窗口的缓存，也不依赖“通常没有并发写入”的假设。任何其他连接提交都会使观察版本变化。观察器本身不可用、关闭失败或 SQLite 返回异常时，运行路径失败安全地回退到原有完整计算。
