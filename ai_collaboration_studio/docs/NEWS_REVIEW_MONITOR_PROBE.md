# 只读状态探针的接入与验收边界

状态：候选组件、原生检查器和单次观察入口已实现，尚未正式部署。`backend/news_review_monitor_probe.py` 提供 `NewsReviewStatusProbe`，供 `MonitorReceiptWriter.run_schedule` 的 `probe` 参数使用。`scripts/run_news_review_observer.py` 绑定新准备身份下的原生进程树检查器；不能把手写的健康字典当作已验证进程，也不能复用已关闭的 20260927A 观察器或授权。

## 准备输入

`target` 固定包含 `identity`（候选提交、激活方案哈希、实际策略哈希）、`policy_id`、实际 `activated_at_ms` 和 `expires_at_ms`、随机端口的 `host_url`，以及两个来源的 `source_standards`。每个来源分别指定 `first_success_ms` 与 `maximum_gap_ms`。实际窗口必须来自激活回执；首个完整成功期限和完整成功间隔必须使用事前审签标准，组件不替用户决定阈值。

调用方必须先核验新准备清单、审批、CI、启动回执、检查器代码哈希及其 PowerShell 7 运行时身份。`inspect_tree` 应执行该检查器，保留所有已登记原生创建 ticks、父子关系和新发现后代。返回结构沿用已验证观察器的 `pins`、`processes`、`listeners`、`owner_pid`、`launcher_pid`、候选/激活/策略身份及完整性标志。枚举缺失或不一致必须标记未完成；owner 文件本身不是持锁或终态证据。本组件不读取 owner 文件、不打开数据库、不推断全部进程终态。

状态读取前、两个 GET 之间和读取后都执行新的进程/端口核验。已登记进程不能从后续结果中消失，宿主原生创建时间不能换代；第七位小数按 100 ns 保存，不能经微秒截断后比较。父启动器已退出而登记子宿主仍在时，继续原窗口内的读取，同时产生独立 `LAUNCHER_EXITED_CHILD_ALIVE` 事件。

## 状态读取边界

- 仅连接 `127.0.0.1`，拒绝受保护端口、域名、认证信息、额外路径和查询参数。
- 每轮只读取 `/api/monitoring/news-review/control` 与 `/api/monitoring/health`。控制响应必须完整匹配实际策略哈希、候选、策略 ID 和原窗口；失败时不发出第二个 GET。
- 不使用代理、不重定向、不重试；连接、响应头、正文读取和解析共用每请求 15 秒截止。截止同时受原到期加 255 秒收尾界限约束，每次阻塞操作只取得剩余预算。头部和正文分别限制大小；有歧义的长度、分块、压缩和重复 JSON 字段均拒绝。
- 返回给回执写入器的只有身份及健康布尔值、来源键。正文、原始模型回复、响应体及异常详情均不持久化。

进程存活、工作线程状态、来源首次成功和最近完整成功分别判断。`pending` 或错误码切换不改变完整成功时间。读取失败、回执损坏或字段缺失只增加不确定性，不能把此前的宿主、线程、来源或父启动器事件通知为恢复。只有新的、未超期的完整回执提供明确恢复证据时才能关闭对应事件。

## 已验证与待完成

隔离回归覆盖进程复用、创建时间相差一个 tick、端口换主、漏掉登记后代、控制身份失败阻断第二次 GET、首个成功期限、pending、父子分离以及失败读取不误报恢复。传输检查使用随机回环端口和模拟慢速分片；真实的两个应用状态处理器也通过新探针读取，未启动来源或模型工作线程。

原生 PowerShell 7 检查器分别枚举 CIM 与原生进程，只取 PID、父 PID 和创建时间，再被动读取本次端口的监听表。CIM 的微秒时间仅用于交叉核对，后续身份始终保留原生 100 ns 精度。PID 集合枚举不一致、相关身份缺失、PID 复用或新发现但不能归属的新孤儿进程均标记检查不完整。当前 Windows 隔离回归实际验证了父启动器退出后登记子宿主仍可见，以及相差一个 tick 的旧身份不能通过。

## 单次观察入口

入口提供激活前等待和已激活目标两种准备格式，均不生成激活文件，也不调用试验启动器。已激活目标使用 `version=news_review_observer_request_v1`、本次 `root`、上文 `target`、`host_receipt_name`、`launcher_pin`、`host_pin` 和全部初始 `pins`。每个 pin 仅含 `pid`、原生精度 `start_utc` 与 `parent_pid`。初始登记必须能沿父链追溯到本次启动器；原生检查会核对实际关系并持续补充后代。这种激活后入口不能补证观察器在激活前已经就绪。

`--prepare --request <请求文件> --powershell <已核验的pwsh.exe> --output <新的方案文件>` 只读核对原准备清单及所列文件、审批、准确候选 CI 回执、启动和激活身份。它将实际策略/窗口、回执哈希、观察器源码和 Python/PowerShell 可执行文件哈希封入方案，不启动观察器、不发送 GET；输出仍标记 `request_authorized=false`。准备过程会执行只读 Git 身份检查。源目录必须是准备候选的干净检出。

`--run --plan <方案文件> --approve-plan-sha256 <明确批准的方案哈希>` 在再次校验全部身份后，独占创建本次根目录的 `monitoring` 子目录。目录已经存在即拒绝，不删除旧证据、不续写重启。观察器保存自己的原生进程 pin，必须独立于被监测树；一旦检查结果包含观察器本身，立即报告独立性失败，禁止 GET。每轮保留进程检查输入和安全输出，再发布监控回执，原生检查器上限为 45 秒。两次完整原生检查均确认全部登记进程退出且端口消失时，结束观察并转交最终核验；缺少宿主报告记为终止故障，不补写报告。观察器只记录报告存在性和哈希，不冒充最终账本验收。

## 激活前等待与同进程切换

新的完整窗口应使用 `version=news_review_observer_wait_request_v1`。请求只包含 `root`、`candidate_sha`、`activation_sha256`、`policy_id` 和 `source_standards`；它们从新准备目录的已复核候选、激活提案和事前审签标准取得。`--prepare` 此时绑定准备清单、CI 和激活提案，并要求尚无实际激活文件。`--run` 仍需明确批准的观察方案哈希。观察器先独占创建 `monitoring` 目录并记录自己的原生进程 pin，再等待试验审批和启动回执；它不会制造这些回执或打开密钥输入。

未激活时每 30 秒检查已有登记进程，保存独立等待回执链，策略哈希明确为 `null`。没有本次宿主 URL 时不查询任意端口，更不发出 GET。启动/激活回执的短暂不完整发布可在方案中固定的 45 秒界限内等待；超过界限、已确认回执改变或消失均失败关闭。等待也受原激活资格期限和初始单调时限限制，回拨不能续期。

实际激活后，原生宿主 pin 来自真实宿主回执，并须匹配等待阶段持续登记的后代。实际策略、窗口、提案、审批、候选和代码/运行时哈希再次核对通过后，才生成**观察绑定回执**。它不是新的激活或审批文件。原观察器进程和全部已登记后代沿用，原生检查序号继续增加，观察目录不重新创建。

激活回执额外记录原激活采样的单调时间区间和计时实现。观察绑定把观察器就绪时的同机 Windows QPC 读数与该区间比较，分别标记“已确认先于激活”“观察到晚于激活”或“顺序未确认”；墙钟排序、缺字段、相等时间或跨越采样区间均不能代替明确的先后证据。独立 watchdog 会重算这一分项。它不单凭该分项宣称实际连续 24 小时验收通过。

独立 watchdog 继续读取同一 `observer-pin.json`，识别等待回执链和一次实际绑定。正常等待和有界的首个 GET 未完成阶段保持安静；等待阶段超过 90 秒无完成检查、进程身份不明、活动阶段超过六分钟无成功读取分别告警。首份真实成功状态回执触发一次激活确认。首次绑定的身份、绑定摘要和活动进程记录会在后续检查中保留；绑定丢失或替换不能退回等待，也不能重置首个读取的宽限期。其他策略的退出回执不能解除当前观察器的存活告警。正常退出回执只触发“需要最终核验”，不把观察器自然退出误称为新的监控故障，也不据此宣布数据库所有权、最终账本或内容质量通过。

## 到期后的原生收尾检查

普通五分钟轮询不再在原到期之后开启新的一轮状态读取；到期前已经开始的有界轮次仍受每请求 15 秒和原到期加 255 秒约束。随后只检查登记进程和原端口，不新增状态 GET。原生收尾间隔固定为 10 秒，单次检查取 45 秒与剩余收尾预算的较小值。绝对收尾期限和观察入口固定的单调期限同时限制等待，回拨不重新发放时间。

这避免五分钟轮询越过只有 255 秒的收尾窗口。两次完整原生检查均确认终态，且原报告存在时，才转最终核验；到界限仍未确认、检查不完整或缺报告仍保留故障，既不杀宿主，也不延长授权。原生检查回执单独留存，不冒充成功健康 GET。

watchdog 核对收尾开始身份、固定期限和原生检查回执链。正常收尾造成的 GET 年龄增长不会新开漏检告警；到期前已经存在的读取或来源问题继续保留，原生检查不能宣告来源/线程恢复。收尾阶段超过 90 秒没有完成原生检查仍告警，到 255 秒仍未确认则报告故障；迟到的退出回执不能证明按时收尾。

收尾开始回执 v2 保留普通轮询实际结束时的墙钟、单调读数及原固定期限。正常回拨可能使单调期限先到，墙钟此时尚未到期；watchdog 会重算原单调期限并核对确实已有一项期限耗尽、收尾读数顺序正确、单调收尾期限没有超过原期限加 255 秒。缺字段、主动停止冒充到期、两项期限均未到或重设期限都不接受。该记录只解释监控阶段转换，不授予应用继续运行或额外请求权限。

这些验证不等于目标部署。目前未安装或授权正式调度，也未绑定正式通知接收器。仍须在新的准备目录部署独立观察器、watchdog 与通知接收闭环，并完成独立复核；配置、通知实际送达和恢复确认必须留证。现有进程树检查器和旧试验原件保留。正式调度、来源请求、付费调用、密钥输入和新激活均未由本入口授予权限。
