# 响应读取失败后的等待期限与可复现验证

本修复基于完整新闻候选 PR #36 的 `d79b9fe47f30d73ce6fffd8202eeffacbf8f1593`，不修改旧 PR #35 的七文件补丁包及其历史记录。PR #36 已包含原先缺失的 `tests/test_news_platform.py`、其余测试依赖和完整后端，因此本轮复用该基线。

## 修复行为

HTTP 响应头已到达、但响应体读取超时或超过大小限制时，运输层已经解析的 `Retry-After` 绝对期限现在继续用于失败调度。此前只保留在诊断中的期限会丢失，调度退回普通退避。

- 已解析期限、仍可用的响应头期限、来源当前等待期限及本地退避取不缩短等待的结果；已接收的绝对期限不会因读取失败重新起算。
- 超出可表示范围的期限保留人工等待；重新打开和手动请求均不能绕过。
- 失败结果写入出错时，原有待恢复机制保留服务器期限，恢复后不提前再次请求。
- HTTP 429、无效 XML、旧冷却恢复压力及历史消息/已读/缓存/回执保留原行为。
- 诊断只接受已解析的有限数值与明确状态，不将原始响应头、正文或异常文本引入调度记录。

这是来源调度修复，没有证据将该缺口归因为 BLS 403，也不证明 BLS 或希捷已恢复。

新增回归实际贯通假响应 → 现有运输层 → 平台调度 → 临时 SQLite 回执，不只检查诊断字典。覆盖 HTTP 200 后读取超时、声明体积超限、流式体积超限、无效 XML、429、人工等待、期限合并、原有压力、事务失败恢复，以及无效诊断数字。
